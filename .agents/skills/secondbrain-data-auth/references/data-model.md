# Data model and request path

## Tables

| Table                  | Key relationships                         | Core fields and rules                                                                                                                                                                               |
| ---------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `profiles`             | `uid` → `auth.users.id`                   | Identity, first-use fields and server-managed `admin` boolean (default false). No subscription JSON column. Billing lives in `subscriptions`; usage lives in `usage_counters`.                      |
| `diary_entries`        | `user_id` → `auth.users.id`               | Unique `(user_id, date)`; text, mentioned people, five nullable mood intensities, timestamps. Date is a date-only value.                                                                            |
| `people`               | `user_id` → `auth.users.id`               | Unique owner plus normalized name (case/spacing); `details` JSONB categories contain dated `{ value, date }` entries. Stable fields preserve actual changes; mentions are derived from diary dates. |
| `audio_transcriptions` | `entry_id` → `diary_entries.id`           | Transcription and audio URL; ownership follows the parent entry.                                                                                                                                    |
| `mood_data`            | `user_id` → `auth.users.id`               | Unique `(user_id, date)`; levels and analysis summary.                                                                                                                                              |
| `subscriptions`        | `user_id` → `profiles.uid`                | One typed subscription per owner; unique Stripe IDs; status, period and cancellation.                                                                                                               |
| `subscription_plans`   | Plan ID                                   | Server-managed monthly chat and report limits.                                                                                                                                                      |
| `usage_counters`       | `(user_id, month, feature)`               | Confirmed and reserved usage; UTC month starts on day 1; nonnegative constraints.                                                                                                                   |
| `usage_reservations`   | Counter FK                                | One reservation per paid operation; idempotent completion/release, 20-minute expiry.                                                                                                                |
| `billing_events`       | Unique provider event ID → profile        | Atomic deduplication and stale-event protection.                                                                                                                                                    |
| `statistics_reports`   | One row → profile                         | Cached analysis output, generated at the server; JSON suits the variable report result.                                                                                                             |
| `billing_email_outbox` | Event ID → billing event; owner → profile | Delivery jobs, leases, attempts and status.                                                                                                                                                         |
| `feedback_requests`    | Request fingerprint → profile             | Legacy mail rate records; new persisted feedback uses `feedback_reports`.                                                                                                                           |

`feedback_reports` stores suggestion/bug messages, owner, workflow status, priority, internal notes, last updater and timestamps. It cascades on owner deletion and has no browser privileges. `submit_feedback` serializes owner submissions, enforces five per hour and deduplicates exact owner/type/message/hour retries atomically.

RLS scopes rows to `auth.uid()` or, for transcriptions, the entry owner. Inspect actual policies and grants before editing; a successful UI check does not prove tenant isolation. Deleting an Auth user cascades through the owner tables and dependent transcriptions.

## Code ownership

- `src/lib/supabase.ts`: browser anon client and server service-role client.
- `src/lib/supabase-operations.ts`: types and CRUD for diary, people, transcriptions, mood, and Auth helpers.
- `src/lib/subscription-operations.ts`: profile mapping, typed subscription writes, quota reservations and authoritative monthly usage RPCs. Profiles read the `subscriptions` relationship; do not add a profile JSON fallback. `UserProfile.subscription` is an application object mapped from that relation, not a profile column.
- `src/contexts/SupabaseAuthContext.tsx`: session-to-app-user/profile synchronization; `src/hooks/useAuth.ts` exposes it.
- `src/lib/api-auth.ts`: bearer-token authentication for route handlers; `src/lib/authenticated-fetch.ts` adds the access token from the current session.
- `src/lib/subscription-policy.ts`: portable, pure plan types/defaults. `subscription-snapshot.ts` returns the server catalogue, effective plan, usage and UTC reset time. `src/middleware/subscription.ts`: compatibility plan checks; despite its directory name, this is application policy, not Next.js request middleware.
- `src/app/api/account`, `subscription`, `statistics`, `stripe`, chat, transcription, and AI routes contain server behavior. Trace the requested route, helper, and client caller together.

## Auth behavior

Email/password, Google OAuth, email verification, password reset, and account deletion use Supabase Auth. Production Site URL is `https://app.lumadiary.com`; allowlist its root and `/reset-password` exactly. Keep `https://app.secondbrainapp.com/**` during the domain migration. The existing Google client and Supabase callback remain unchanged. Hosted email subjects/templates use LumaDiary; verify the entire editor contents after saving, because replacing only a visible editor slice can leave old HTML behind. The reset helper sends an explicit `redirectTo` based on the current origin. A Google-linked account may have `email` as its primary provider while `app_metadata.providers` includes `google`; use that provider array when deciding whether Google is available.

For a new private route: authenticate first; validate payload shape and size; derive or check the owner from the verified token; fetch only owner-scoped resources; enforce plan/usage on the server when it has a cost; return no personal data in logs or error details. Webhooks instead verify the provider signature using the raw body.

## Ownership and regression checks

Account deletion calls `POST /api/account` with the current bearer token; the server derives the account ID. AI extraction with an entry ID calls `getEntryByIdForUser` before model or database writes, and requires the entry date to match. Verify Stripe session ownership before returning payment status and never include another session in an error response. Background expiry must check write errors before counting a profile as expired. Run the API/data suites and local PostgreSQL security tests described in [docs/TESTING.md](../../../../docs/TESTING.md); simulated browser responses do not establish RLS.

## Quota and billing invariants

Authenticate cost-bearing routes before `reserve_usage`. Never accept a browser counter as authority or update a whole JSON document for usage. Reserve before calling a provider, then confirm once on success or release on failure. Transactions must finish before external calls. `read_monthly_usage` reclaims expired holds. The effective paid plan requires active status and an unexpired period; plan changes preserve the same month's consumption.

When diagnosing a manually changed plan, inspect `subscriptions.plan`, `status` and `current_period_end` together. Changing only `plan` leaves an inactive subscription with free access. A null period end currently means no expiry; do not silently grant that for normal paid billing. Manual grants require the owner's explicit intent, an exact owner-scoped update and verification in both SQL and the authenticated UI. Refresh the subscription snapshot after the change; never loosen authorization to accept inactive paid plans.

`complete_statistics_report` persists the report and its charge atomically. Graph queries are free after server-side paid-plan authorization; only complete report regeneration consumes statistics quota. Summary/quote GET routes read cache only. Use actual diary mentions for rankings, and explicit read errors instead of fabricated empty statistics.

`GET /api/statistics/analytics?period=all|7|30|90|365` authenticates and checks the effective paid entitlement before either diary or report reads. Derive `user_id` from the token, ignore client owner parameters, paginate diary dates with an owner-scoped ascending keyset and select only aggregation inputs. Finite windows include an equal previous period; all-history reads must not silently stop at Supabase's row cap. `diary-analytics.ts` excludes future/blank entries, counts distinct diary dates, preserves null mood scores and uses owner-scoped people catalogue names for canonical display. `person-mentions.ts` resolves only unambiguous references to the writer’s own parents when an existing parent name and relationship agree; a separate “madre de …”, ambiguous catalogue or dated fact is never proof of identity. It also recovers an omitted explicit “mi madre”/“mi padre” reference from diary text without calling AI. Reuse that canonical resolution when validating new AI extraction output, deduplicate after resolution, and count each person once per saved diary date. Read both diary and people with owner-scoped keyset pagination; never silently cap a catalogue. Return aggregates plus the existing report generation date, never diary text; use private no-store headers. Timeline points include UTC `timestamp`, actual sampled `startDate`/`endDate` and `samples`; a point with scores must be anchored to an existing analysed diary date. Sparse long diaries preserve all daily points with null separators; dense older buckets are bounded, while the latest 30 days remain daily. Tooltip/table must disclose multi-entry means and their range; global per-emotion averages use original entries, never averages of bucket averages. This GET uses no provider calls or quota reservations. The browser's free preview uses synthetic constants and makes no statistics requests. Report POST remains the sole explicit paid AI operation; opening or filtering statistics must never POST a report.

Stripe webhook signature verification precedes `apply_billing_event`. Event identity, provider timestamp, subscription mutation and mail enqueue belong to one transaction; re-read current provider state for late events. Browser checkout verification must not grant access. Preserve customer references when a paid period ends. Restrict quota and provider RPC execution to `service_role`; give the browser only owner-scoped SELECT. Trigger functions use fixed empty search paths and have no direct public execute privilege.

The executable local schema and concurrency/security checks are in `tests/database/`; release and integration contracts are documented in [docs/SUBSCRIPTIONS.md](../../../../docs/SUBSCRIPTIONS.md).

Hosted Supabase default privileges may grant ALL on new public tables. Explicitly revoke browser grants before granting SELECT, including on the plan catalogue: RLS does not protect TRUNCATE. Local database verification mirrors broad default privileges and checks that catalogue updates and TRUNCATE are denied. Index billing foreign keys used for owner reads or cascades. Keep deployed migration filenames aligned with the versions registered by the migration tool.

Profile creation provisions the free normalized subscription through `profiles_subscription_default` / `create_profile_subscription()`. Keep this trigger when changing profiles. Subscription changes never write profiles; there is no projection trigger or legacy Stripe JSON index. Apply new schema through ordered migrations rather than editing already-applied SQL. `supabase-schema.sql` is the historical bootstrap used before the migration chain; the final schema is defined by the full chain.

The current billing contract includes a service-only schema-version RPC and atomic provider-event protection across subscription IDs. A late event of another subscription must not replace the current one; replacement requires an accepted new creation/payment event after the previous subscription is inactive/canceled. Reject customer reassignment and deduplicate before mutating/enqueuing. Browser roles cannot read internal billing events, email jobs, feedback rate records or quota reservations; those have server consumers only. Public subscription/counter/report reads remain owner-scoped.

Before deleting Auth identity, reconcile and close its Stripe billing through the server. Keep the account when provider confirmation fails, and never permit a client customer ID to select another person's billing. Check [the activation matrix](../../../../docs/PAYMENTS-ACTIVATION.md) for schema gates and account-deletion cases.

`billing_checkout_attempts` is an internal table with one row per profile, cascading on deletion and no browser access. `claim_checkout_attempt` serializes reservation against the subscription row, preserving the first request UUID/plan across concurrent tabs. Expiry is 36 minutes; an unregistered attempt may be replaced after six minutes to retain Stripe's minimum 30-minute session lifetime. `register_checkout_session` accepts only the matching, unexpired attempt and the same provider session. Both RPCs are service-only. Release requires owner plus exact request UUID after provider expiration; never unlock an unpaid session while it is still payable.

## Person information integrity

Statistics add per-person means with independent emotion denominators, analysed-entry counts and up to 12 latest dated scores, plus unordered co-occurrence pairs. Each canonical person/pair counts once per saved date, respects the selected period, and never exposes diary text in the overview. Canonical mention recovery and normalization must be identical for graph generation and detail validation.

`GET /api/statistics/connections` takes source/target names, period and up to 12 dates from a selected graph edge. Authenticate and require an effective paid plan before reading either catalogue or diary. `statistics-data.ts` supplies the shared owner-scoped keyset catalogue reader. Validate real dates within the period; query only the verified owner's requested dates and independently recheck both canonical mentions. Dates and pair names are selectors, not authorization. Return only those entries' saved emotion values and plain-text excerpts of at most 201 characters (200 plus ellipsis), with private no-store headers. Never invoke AI, consume quota or load all diary text for this interaction. No database mutation or new table is involved.

`GET /api/statistics/person-emotions` independently authenticates/authorizes and returns up to 12 matching dates with saved scores, ordered by the whitelisted emotion descending, then date descending. The full selected period is eligible, including old high scores. Validate the optional numeric-score/date cursor before composing a PostgREST OR keyset; every query still filters the verified owner, date window and valid score range. Use the same canonical mention resolver as the overview, including unambiguous parent recovery. Scan at most two batches of 100 candidate rows per request, returning a continuation after the last processed row even when rare mentions yield fewer than 12 results. Do not use OFFSET, silently cap history, include unanalysed values as zero, return content or charge quota. The client can explicitly continue until exhausted; a cursor selects position, never ownership. No new schema or database write is involved.

`person-information.ts` is the shared normalization/merge contract, mirrored by PostgreSQL `normalize_person_details`. Profile fields (`rol`, `relacion`, `cumpleaños`, `direccion`) collapse consecutive equivalent observations while preserving genuine changes and returns (A → B → A). Keep the first known date of an unchanged value; unknown placeholders do not become facts. Events in `detalles` deduplicate equivalent spelling only on the same date; recurring activities on different dates remain separate. Preserve accents, unique facts and undated legacy values. Do not automatically erase semantic paraphrases or merge people merely because their names look similar.

`people_information_integrity` normalizes every write and sets a server `clock_timestamp()` version. AI merges use owner-scoped compare-and-swap on `updated_at`, re-reading before retrying a concurrent update/create. Manual editing supplies the version captured when editing began; a conflict keeps the draft and asks the user to reopen. A read or save failure is not an empty address book or successful extraction.

`mention_count` counts distinct diary dates with a matching name in `mentioned_people`; never increment it for model calls. Diary insert/update/delete refresh only affected owner names. `people_rename_mentions` rewrites that owner's diary references within the rename transaction. Integrity triggers have fixed search paths, check browser ownership and no direct API EXECUTE grants. The private `person_information_repair_backups` table preserves pre-repair details/counts, cascades on owner deletion, and grants no browser access or TRUNCATE. Before a historical cleanup, preview the transformation and keep a recoverable owner-scoped snapshot; never put personal snapshots in the repository.

The extraction route uses strict structured output and validates the full response before writes. Include all mentioned people even with no new facts so diary membership stays accurate. Context uses stable values known at the entry date, not future observations, plus facts already recorded on that date. Mood failures return a partial warning without fabricated defaults. Individual chat loads its canonical person by verified owner and ID on the server, ignoring browser-supplied profile facts.

## Operational administration

Read [docs/ADMINISTRATION.md](../../../../docs/ADMINISTRATION.md). `/api/dashboard/*` validates the bearer identity and fresh `profiles.admin` before any cross-owner query. Every service-only RPC repeats the flag check; never authorize from editable metadata or the local profile. Exclude `admin` from browser INSERT/UPDATE column grants. No account is automatically promoted. User directory/overview use verified Auth identity, effective subscriptions and SQL aggregates with bounded page/detail responses; do not expose diary content. Auth table access is isolated to `dashboard_private.accounts(actor)` with fixed empty search path, explicit actor check and only service-role EXECUTE. Keep the private schema unavailable to browser roles. Report triage requires its original `updated_at` and records `updated_by`; conflicts must preserve the admin draft. RLS and explicit revokes protect internal feedback, notes, billing events/mail jobs and quota reservations.

## Emotional score contract

Current analysis and statistics read `diary_entries.happiness`, `tranquility`, `stress`, `sadness` and `neutral`. `MOOD_KEYS` is the shared whitelist; each score is an independent 0–100 intensity, not a share summing to 100. Null/absence means unevaluated or insufficient evidence and must never become a zero, neutral score or denominator sample. Neutral describes an emotionally unmarked experience, never a descriptive writing style or the share of factual sentences; it is distinct from tranquility and is never calculated as a complement of other emotions. Strict model output includes all five keys with numeric or null values; malformed output raises the existing partial-analysis warning without overwriting saved scores.

The additive `neutral_diary_emotion` migration defines nullable numeric `diary_entries.neutral`, a 0–100 CHECK and a partial `(user_id, neutral DESC, date DESC)` ranking index. Historical rows remain null; no automatic backfill, provider calls or changes to existing scores. Existing owner RLS remains in force. `mood_data.neutral_level` is legacy and is not the statistics source. Select the five columns explicitly (literal column lists preserve Supabase TypeScript inference), include neutral-only analysis in mood reads, and preserve null in API mappings. `mood-distribution.ts` normalizes only the overview presentation to percentages. Storage, API data, calendar dominance, person means and emotion rankings retain original independent intensities and nulls. A zero denominator yields no shares; partial shares disclose missing dimensions. The model prompt/schema/parser lives in `mood-analysis.ts`; add future dimensions to both the shared keys and the SQL/API/UI contract with local SQL and owner-isolation tests.

## Administrative diary reanalysis

See [administration](../../../../docs/ADMINISTRATION.md). `diary_reanalysis_jobs/items` are service-only RLS tables, with one active job per owner and globally unique start request UUIDs. Snapshot only entry IDs/dates/version fingerprints; no copied diary content. Atomic stored counters avoid rescanning the job for each item. Existing `mood_analyzed_at` distinguishes prior complete analysis from pending work: recalculate only emotions for the former, extract people and moods for the latter. Use shared `diary-analysis.ts` for prompt/schema/validation and bounded provider timeouts.

Fresh admin checks in both API and every RPC precede access. `admin_claim_reanalysis` serializes one live provider lease per job; expired leases fail for explicit retry. `admin_finish_reanalysis` verifies owner, job/entry/token, expiry and source version; saves five nullable intensities and pending people/membership atomically. Prepared person updates must include the current UUID/version and normalized merged details. Validate all versions before writes; rebase conflicts using the same model output, never another AI call. Source changes/deletion and canceled/stale leases cannot write. No user quota, report generation, diary content replacement or diary insertion occurs. Browser responses expose only summary/date/code; never return claims. Start/retry/cancel are idempotent and preserve completed items.

The public plan catalogue exposes `prices` in EUR major units, plus `currency` and `interval`, from root `shared/plan-pricing.json`. Database `subscription_plans` remains the source of usage limits; commercial prices are not stored in that table.
