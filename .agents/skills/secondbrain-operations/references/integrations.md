Auth provider settings live in the Supabase dashboard: Google OAuth client credentials, authorized redirect `https://<project-ref>.supabase.co/auth/v1/callback`, site URL/redirect allowlist, and custom SMTP. Do not paste a Google client secret into `NEXT_PUBLIC_*`. Password recovery uses the app's current origin as `redirectTo`; make sure the deployed origin is allowlisted and reachable.

The app workspace is `secondbrain/` (Next 16); the marketing workspace is `secondbrain-landing/` (Next 15). The app's Vercel project is `secondbrain-app`, its Root Directory is `secondbrain`, and its production hostname is `app.lumadiary.com`. The landing uses `www.lumadiary.com`. Confirm the correct project before changing env vars or deploying. Domain DNS is managed separately from Vercel project assignment and TLS. For a release, check `npm run build` in both workspaces; each build checks for numbered conflict copies before Next compilation. Check preview HTTP and authenticated behavior, live environment configuration, Auth redirect, mail delivery, and any payment/webhook flow being enabled. A successful build alone does not confirm the domain, external Auth, mail, or Stripe services.

For a Vercel Domain Error, inspect the build result and alias assignment separately: a deployment can be `READY` while `aliasError` records a failed domain assignment. Verify the domain is attached to the intended project's Production environment, points to the intended commit, and serves HTTPS with a valid certificate. Resolve stale or conflicting domain associations before retrying the same source deployment; do not change application code to repair an alias collision.

Keep existing payment maintenance routes available even when new checkout is disabled. A cancellation tied to a real Stripe subscription must succeed at Stripe before the app records it as scheduled; return an error instead of inventing a renewal date if Stripe fails.

## OpenAI model contract

The canonical identifiers are in `secondbrain/src/lib/ai-models.ts`: all text features use `gpt-6-luna`, and speech-to-text uses `gpt-transcribe`. Both use the existing server-only `OPENAI_API_KEY`. The app pins the OpenAI Node SDK to `7.25.0` for typed support of the current request fields.

Stylization, person extraction, emotional analysis, summaries and quotes use Responses with `reasoning.effort: low` and `text.verbosity: low`. Personal and person chats keep Chat Completions without tools, existing history and sampling settings, with `reasoning_effort: none` and `max_completion_tokens` limits. Do not restore `minimal` or the legacy `max_tokens` parameter. If enabling reasoning in chat, remove sampling fields such as `temperature` as required by the API.

Person extraction and emotional analysis use strict Responses `text.format` JSON schemas plus application validation. Known people with unchanged facts still appear in the returned membership. Repeat attempts never increment mentions; PostgreSQL derives them from saved diary dates. Do not treat malformed output or database persistence failure as success, and never manufacture default emotional scores.

Transcription uses `/audio/transcriptions`, `languages: ['es']` as a language hint, and the JSON response's `text`. Preserve actual recording MIME and bytes; set an extension matching the MIME rather than labelling every upload MP3. Keep the 25 MB provider file ceiling and reject empty transcripts. Existing app return fields stay `text` and `audioUrl`; the provider's detected languages do not change this contract.

Transcription availability errors return safe Spanish messages and stable codes: `AI_CREDITS_EXHAUSTED` / `AI_RATE_LIMITED` use HTTP 503; other provider failures use 502. Do not forward raw provider errors or log their headers/cookies. Lack of OpenAI credits requires replenishing the API project's balance; changing the user's SecondBrain plan does not restore provider availability.

Official references: [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [GPT-6 parameter compatibility](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters), [file transcription](https://developers.openai.com/api/docs/guides/speech-to-text). Model access and billing still depend on the OpenAI project behind the deployed key; mocked tests do not establish that access.

## Billing and email contract

Read [docs/SUBSCRIPTIONS.md](../../../../docs/SUBSCRIPTIONS.md) for the normalized schema, UTC quotas, provider/worker flow and release dependencies. Apply the versioned database schema before a release that consumes new tables/RPCs; verify live rows and privileges. Profiles have no billing JSON column: use normalized subscription relations and quota RPCs. Do not roll back to code that reads or writes the removed profile field. Retain existing provider references and historical usage.

Stripe Node 22.6.2 uses its typed API `2026-08-26.dahlia`: subscription dates are on items, invoice relationships under `parent.subscription_details`. Webhooks re-read provider state, and commit their unique event, subscription state and mail queue together. Return-page verification reads only. Checkout/customer creation have stable idempotency keys; an existing subscription goes to Customer Portal. Configure/test the portal's products, allowed changes, proration and locale before enabling billing. Both checkout and portal remain disabled by the explicit checkout flag. New checkout validates provider price currency, unit amount and monthly interval against the advertised euro plans.

Transactional email layout and escaped content live in `src/lib/email-templates.ts`. Regenerate portable Supabase Auth templates, subjects and synthetic previews with `node scripts/build-email-previews.mjs`. Version the templates; applying them to hosted Auth is a separate release action. Use official ConfirmationURL/Token placeholders, Spanish copy and accessible single-column tables. Do not enable security notifications without preparing their corresponding templates.

Feedback first persists in `feedback_reports` via atomic `submit_feedback`; optional Resend notification uses the authenticated sender and an idempotency key. A missing key or delivery failure does not reject a saved report. The admin-only `/dashboard` reads SQL aggregates and manages the report workflow. Apply its versioned schema and explicitly identify the first admin account before granting `profiles.admin`; see [administration](../../../../docs/ADMINISTRATION.md). Billing mail is queued with provider events; its worker is gated by `BILLING_EMAILS_ENABLED` and `CRON_SECRET`, selects confirmed Auth recipients and claims jobs with `SKIP LOCKED`. Lease is ten minutes, retries stop after five attempts or 23 hours (before provider idempotency expires). Monitor failed jobs when scheduling the worker. Tests use fake recipients and never send real messages.

Checkout keeps one client request UUID per mounted user/plan attempt. The database reserves one shared attempt per owner across tabs through `claim_checkout_attempt`; the server uses that reservation's UUID and fixed expiry for Stripe idempotency. A pending different plan must be explicitly canceled, not silently replaced. `cancel-checkout-session` expires the owned unpaid provider session before releasing its exact reservation; a completed payment cannot be canceled this way. Ignore checkout replies after account/plan changes. Avoid logging billing contact details in the browser.

## Activation and dependency contract

Use [the payment activation guide](../../../../docs/PAYMENTS-ACTIVATION.md). `APP_BASE_URL` supplies a trusted HTTPS billing origin, defaulting to `https://app.lumadiary.com`; never derive payment redirects from request host headers or client URLs. Checkout success returns to `/billing/return?session_id=…`; `/dashboard` is reserved for administration. Hosted checkout uses server-returned URLs and requires no browser publishable key. The integration identifier is stable per integration, not a new checkout attempt identifier.

Checkout/portal/catalogue availability and webhook processing require `billing_schema_version()` to return 2 from the server. The versioned SQL protects the current subscription against a later event from another subscription and keeps internal events/jobs/reservations inaccessible to browser roles. Apply that migration before enabling billing, without changing already-applied migrations. Active provider status alone does not grant paid access: expand/reconcile the latest invoice and require `paid`. Never treat a failed browser return as permission to create another subscription.

`npm run check:billing -- --remote` validates the sandbox account, prices, current database schema, existing ownership/mode references, signed webhook configuration and default portal with read-only calls. `--live` checks live mode. The script does not create or cancel anything and does not prove successful signed delivery or payment acceptance; complete the sandbox matrix first. Do not silently clear an old provider reference because it cannot be retrieved with a different key mode/account.

Account deletion closes open checkout sessions and removes the verified Stripe customer before Auth deletion; this cancels future renewals immediately. Normal subscription cancellation remains at period end. Confirm ownership before any cancellation/deletion. A deleted customer permits acknowledging later subscription events without recreating the account.

Install at the repository root with `npm ci`; the root lockfile is canonical for both workspaces. Next app/landing are pinned separately and both set the root for output file tracing. Compatible security overrides for PostCSS/Sharp are declared at the root; preserve and audit them during dependency updates. Run both normal builds and the full tests after changes; tests use `.next-test` separately. Do not equate a passing npm audit or mock suite with remote provider availability, email delivery or real billing verification.

Administrative reanalysis needs the additive `admin_diary_reanalysis` migration before its API/UI release and uses the existing server OpenAI/Supabase keys. It runs one entry per authenticated admin request, with 90-second provider timeouts, no SDK retries and a 240-second route duration; verify the hosting duration limit. Progress is durable, while further requests run only with the admin dialog active. No new cron, worker, public key or automatic historical analysis is enabled. A provider outage stops advancement for explicit retry. Never run a real owner's history merely to verify deployment; use synthetic API/E2E data and disposable SQL/concurrency tests, then read-only live grants/count checks.


## Synthetic emotional-analysis evaluation

`npm run eval:mood` is a separate, explicit provider evaluation, excluded from CI/default tests. It loads the local server-only OpenAI key and uses the exact shared `analyzeDiaryMood` prompt/model/parser on four built-in fictitious cases (routine, descriptive enjoyment, descriptive pressure, simultaneous humor/pressure), two calls at a time with existing bounded timeouts/no retries. It consumes provider credits but never reads/writes Supabase, processes a real owner's entries, changes quotas or sends email. Broad score bands check direction rather than pretending there is one objective human score. Output contains only case IDs and synthetic scores. A prompt change affects future explicit analyses; use the existing per-user dashboard reanalysis action when the owner deliberately wants to recompute history.

## Shared plan pricing

`shared/plan-pricing.json` is the canonical monthly EUR price contract in cents (Pro 499, Elite 999). Both workspaces expose it through `src/lib/plan-pricing.ts`; plan cards, public catalogue amounts, SEO offers, Stripe checkout validation and the readiness script derive prices from it. Stripe price amounts are immutable: provision matching prices and update configured IDs before releasing a price change. Inspect existing subscriptions before replacing IDs because subscription reconciliation maps those IDs to plans. Do not activate checkout as a side effect of changing prices.

## Live checkout and commercial settings

Hosted checkout requires explicit acceptance of the public terms, links to the privacy policy, and discloses monthly automatic renewal and the 30-day refund guarantee. Configure both URLs in Stripe's public business details before enabling this flow. Public seller information is centralized in the landing's `src/lib/business.ts`; changes to seller or refund policy must update the legal pages and checkout disclosure together. Refund requests are handled through the published support mailbox; publishing a policy does not issue automatic refunds.

Prices use inclusive tax behavior to preserve the advertised final amounts. Inclusive prices do not calculate or remit tax: verify active registrations and a successful calculation before enabling automatic tax. Never infer registration from a NIF or an enabled Stripe account. Portal upgrades use `always_invoice` with the billing date unchanged; decreases are scheduled at period end and cancellation keeps the paid period. Payment method updates and invoice history are enabled. Readiness retrieves the default portal with `features.subscription_update.products` expanded because Stripe omits this field from ordinary responses.

Use a dedicated restricted live key in Vercel Production, separate from sandbox Preview. Runtime access needs customers, Checkout and portal sessions, subscription maintenance, and read access to prices and invoices; catalog/portal/webhook configuration additionally needs their write permissions. Do not grant access to payouts or transfers. Confirm actual endpoint delivery and complete sandbox flows before enabling checkout.
